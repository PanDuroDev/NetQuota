# Network monitoring

## Providers

`crates/monitor` exposes two independent providers behind stable types, so the
quota engine never depends on how bytes were counted.

### 1. Interface counters (`global.rs`)

`GetIfTable2` returns `MIB_IF_ROW2` entries with 64-bit `InOctets`/`OutOctets`
straight from the NDIS layer.

- Exact byte counters maintained by the driver stack, no sampling.
- Readable without elevation, so the desktop app works while the service is off.
- Filters: `OperStatus != IfOperStatusUp`, loopback, and NDIS filter layers.
  Filter layers are the important part: WFP/QoS filter instances report the same
  traffic again, and without the filter this machine read **51.81 GB** where the
  physical adapter reported **12.96 GB**.
- VPN: tunnel interfaces (`IF_TYPE_TUNNEL`, WireGuard/Tailscale/OpenVPN
  descriptions) are summed separately. If a physical adapter is present, only
  physical adapters feed the total, otherwise the tunnel would count the same
  bytes twice.

Verified on the development machine: `down 12.96 GB`, `up 794.7 MB`, Ethernet
plus three zero-byte Wi-Fi Direct adapters plus a Tailscale tunnel.

### 2. Per-process accounting (`etw.rs`)

Real-time ETW session `NetQuota-KernelNetwork` on provider
`Microsoft-Windows-Kernel-Network`
(`7dd42a49-5329-4832-8dfd-43d979153a88`).

Counted events (data transfer only):

| Event | Meaning |
| --- | --- |
| 10 / 11 | TCPv4 send / receive |
| 26 / 27 | TCPv6 send / receive |
| 42 / 43 | UDPv4 send / receive |
| 58 / 59 | UDPv6 send / receive |

Deliberately excluded: 12/15 connect, 13 disconnect, 14/30 retransmit, 17/49
failure, 18/34 protocol copy. Retransmissions are excluded because the interface
counters already include the bytes and counting them separately inflates
per-process totals.

Payload layout (verified against the provider manifest from
`wevtutil gp Microsoft-Windows-Kernel-Network /ge:true /gm:true`):

| Offset | Field |
| --- | --- |
| 0 | `u32` PID |
| 4 | `u32` byte count |
| 8 | 16-byte source address |
| 24 | 16-byte destination address |
| 40 | `u16` source port |
| 42 | `u16` destination port |

Only the first 8 bytes are required; addresses are read when the record is at
least 44 bytes.

Requirements and limits:

- Requires administrator or membership in **Performance Log Users**. The service
  runs as LocalSystem. Unelevated runs fail with `StartTraceW` error 5 and the
  status becomes `degraded` instead of pretending there is data.
- Kernel events describe IP traffic. Traffic from processes whose packets are
  generated by another process, or by the kernel on their behalf, is attributed
  to the emitting PID.
- QUIC/HTTP3 is UDP, so it is covered by the UDP events.
- VPN tunnelling shows up twice at different layers. Because only the outer
  packet exists at the IP layer, the outer interface total and the per-process
  total stay consistent; the tunnel is excluded from the global sum when a
  physical adapter is present.
- Short-lived processes can exit before their PID is resolved. Their bytes are
  still counted in the global total, and the app is reported as `Unknown` with
  `confidence: unknown` rather than being dropped silently.

The event callback has no context parameter, so records go through a
process-global queue with a 65,536-event cap and a dropped counter. Dropped
events are surfaced in the snapshot instead of being hidden.

## Identity

`app_key` is derived from the normalized executable path (lowercased), falling
back to `name:<exe>` when the path is unavailable. `svchost.exe` instances are
keyed by the sorted set of hosted services from the SCM
(`svchost.exe#dnscache+dhcp`), so different service groups are different apps.
PID reuse is detected by comparing process creation time: a new creation time
resets the per-instance counters and marks attribution `estimated`.

Publisher comes from the `CompanyName` version-resource field. It is metadata,
not an Authenticode check, and is labelled as publisher metadata in the UI.

## Confidence model

| Value | When |
| --- | --- |
| `measured` | ETW resolved the PID and its executable for the whole interval |
| `estimated` | PID was resolved after some events, or reuse was detected mid-interval |
| `unknown` | Process could not be opened or had already exited |

The UI never presents `estimated` or `unknown` as exact, and the quota engine
does not hard-block on `unknown` attribution.

## What was not used, and why

- `GetExtendedTcpTable` / `GetExtendedUdpTable`: connection ownership only, no
  byte counts. Useful for a "who is connected" view, not for quotas.
- `GetPerTcpConnectionEStats`: TCP-only, sampling-based, and expensive per
  connection; cannot see UDP/QUIC.
- Windows Filtering Platform callouts: exact and able to shape, but needs a
  signed kernel driver. Left as a future provider.
- `NetworkList` COM for metered state: not exposed by the `windows` crate. WinRT
  `NetworkInformation::GetConnectionCost` is used instead.

## Overhead

Measured steady state on the development machine: one ETW session, 1 Hz polling,
5 s aggregation. The service writes at most one row per app per hour plus policy
and event writes, so disk activity is proportional to the number of active apps,
not to packet count.
